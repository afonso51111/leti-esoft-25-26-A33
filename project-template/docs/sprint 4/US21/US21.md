# US21 - Schedule the vaccine administration at a vaccination center

## 1. Requirements Engineering

### 1.1. User Story Description

As an SNS User, I want to schedule the vaccine administration at a vaccination center.

### 1.2. Acceptance Criteria

* **AC1:** The user must select a Vaccination Center.
* **AC2:** The user must select a Vaccine Type.
* **AC3:** The system must validate if the selected time slot is available at the center.
* **AC4:** The user cannot have another appointment for the same vaccine type if the process is not complete.

### 1.3. Found out Dependencies

* **US1:** It is necessary to have Vaccination Centers registered.
* **US12:** It is necessary to have Vaccine Types registered.
* **US2:** It is necessary to be a registered SNS User.

### 1.4 Input and Output Data

**Input Data:**
* Selected data:
  * Vaccination Center
  * Vaccine Type
* Typed data:
  * Date
  * Time

**Output Data:**
* List of Vaccination Centers.
* List of Vaccine Types.
* Confirmation of the scheduled appointment.

## 3. Design

### 3.1. Realization of Functionality

The design follows the **Layered Architecture** with **Service** and **DTO** patterns. The process involves multiple steps of data retrieval (Centers, Types) before the final action (Scheduling).

1. **UI**: Handles the interaction sequence (Select Center -> Select Type -> Input Date).
2. **Controller**: Forwards requests to the Service.
3. **Service**:
  * Retrieves lists of Centers and Vaccine Types from Repositories for the UI (via DTOs).
  * Orchestrates the creation of the `Appointment`.
  * Fetches the full domain entities (`SNSUser`, `VaccinationCenter`, `VaccineType`) based on DTO IDs.
  * Creates the `Appointment` object.
  * Saves it using the `AppointmentRepository`.
4. **Repositories**: Provide access to domain aggregates.

| **Step 7** | ... creates the object? | `Appointment` | **Creator**: The domain object is instantiated. |
| **Step 8** | ... persists data? | `AppointmentRepository` | **Repository**: Saves the appointment. |
