# US 14 - Register an employee

## 1. Requirements Engineering

### 1.1. User Story Description

As DGS Administrator, I want to register an employee.

### 1.2. Customer Specifications and Clarifications

**From the specifications document:**

> AC14-1: Each employee must be assigned a single function/role within the system.
> AC14-2: The attributes Name, Phone Number, and E-mail Address are mandatory.
> AC14-3: The Phone Number and Citizen Card Number must comply with the Portuguese format.
> AC14-4: The Phone Number and E-mail Address must be unique across all registered employees.

**From the client clarifications:**

> **Question:** What defines an "employee" and their "role"?
>
> **Answer:** We assume an employee is defined by several attributes (Name, Address, Phone, Email, CC). The "role" (e.g., "Nurse", "Receptionist") determines the type of employee.

### 1.3. Acceptance Criteria

-   **AC14-1:** The system must allow the administrator to select the employee type (Nurse or Receptionist).
-   **AC14-2:** The attributes Name, Address, Phone Number, and E-mail Address are mandatory.
-   **AC14-3:** The Phone Number and Citizen Card Number must comply with the Portuguese format.
-   **AC14-4:** The Phone Number and E-mail Address must be unique across all registered employees (global validation).
-   **AC14-5 (derived):** Name cannot be empty.
-   **AC14-6 (derived):** Phone Number must have 9 digits and start with '9' (Portuguese mobile format).
-   **AC14-7 (derived):** E-mail Address must be in a valid format.
-   **AC14-8 (derived):** Citizen Card Number must have 9 alphanumeric characters (Portuguese format).

### 1.4. Found out Dependencies

-   US15 (“As Administrator, I want to get a list of employees assigned to a specific function/role”) has a direct dependency on this US. This US creates the instances (Nurse/Receptionist) that US15 will list.

### 1.5 Input and Output Data

**Input Data:**

-   Typed data:
    -   Name
    -   Postal Address
    -   Phone Number
    -   E-mail Address
    -   Citizen Card Number
-   Selected data:
    -   Employee Type (Nurse or Receptionist)

**Output Data:**

-   (In)success of the operation

## 3. Design - User Story Realization

### 3.1. Rationale

| Interaction ID | Question: Which class is responsible for...       | Answer                     | Justification (with patterns)                                                                                                             |
|:--- |:--------------------------------------------------|:---------------------------|:------------------------------------------------------------------------------------------------------------------------------------------|
| Step 1 | ... interacting with the actor?                   | RegisterEmployeeView       | Pure Fabrication: there is no reason to assign this responsibility to any existing class in the Domain Model.                             |
| | ... coordinating the US?                          | RegisterEmployeeController | Controller                                                                                                                                |
| Step 2 | ... getting the list of roles/types to show?      | RegisterEmployeeController | Controller: Can provide the supported types (Nurse/Receptionist) directly or via system configuration.                                    |
| Step 3 | ... requesting data and type selection?           | RegisterEmployeeView       | IE: is responsible for user interactions.                                                                                                 |
| Step 4 | ... saving the inputted data?                     | RegisterEmployeeView       | IE: is responsible for keeping the inputted data.                                                                                         |
| Step 5 | ... showing all data and requesting confirmation? | RegisterEmployeeView       | IE: is responsible for user interactions.                                                                                                 |
| Step 6 | ... instantiating a new employee?                 | DGS Administrator          | Creator (Rule 1): In the Domain Model, DGS Administrator "manages" Employees.                                                             |
| |                                                   | EmployeeContainer          | By applying High Cohesion + Low Coupling, DGS Administrator delegates this to `EmployeeContainer`.                                        |
| | ... deciding which class to instantiate?          | EmployeeContainer          | **Factory/Creator**: The container receives the "type" selected and instantiates the correct subclass (`Nurse` or `Receptionist`).        |
| | ... knowing the EmployeeContainer?                | DGS Administrator          | IE: knows the EmployeeContainer to which it delegates responsibilities.                                                                   |
| | ... validating all data (local validation)?       | Employee (Base Class)      | IE: The base class `Employee` validates common attributes (phone, email format) in its constructor.                                       |
| | ... validating all data (global validation)?      | EmployeeContainer          | IE: knows all Employees (regardless of subclass) and can check for uniqueness of Email/Phone. (AC14-4)                                    |
| | ... saving the created employee?                  | EmployeeContainer          | IE: is the "container" for all Employee objects.                                                                                          |
| Step 7 | ... informing operation success?                  | RegisterEmployeeView       | IE: is responsible for interactions with the user.                                                                                        |

## 4. Tests

Three relevant test scenarios are highlighted next.

**Test 1:** Check that it is not possible to create an instance of a specific Employee subclass with invalid/missing values.

    TEST_F(EmployeeFixture, CreateNurseWithEmptyName){
        // Tenta criar um Enfermeiro com nome vazio
        EXPECT_THROW(new Nurse(L"", L"Address", L"912345678", L"test@test.com", L"12345678A"), std::invalid_argument);
    }

    TEST_F(EmployeeFixture, CreateReceptionistWithInvalidPhone){
        // Tenta criar um Rececionista com telemóvel inválido
        EXPECT_THROW(new Receptionist(L"Ana", L"Address", L"123", L"test@test.com", L"12345678A"), std::invalid_argument);
    }

**Test 2:** Check that the container creates the correct subclass type.

    TEST_F(EmployeeContainerFixture, CreateCorrectSubclasses){
        // Cria um enfermeiro via container
        shared_ptr<Employee> emp1 = this->container->create(L"Ana", ..., "Nurse");
        // Verifica se é do tipo Nurse (usando dynamic_cast ou verificação de tipo)
        EXPECT_NE(dynamic_pointer_cast<Nurse>(emp1), nullptr);

        // Cria um rececionista via container
        shared_ptr<Employee> emp2 = this->container->create(L"Rui", ..., "Receptionist");
        EXPECT_NE(dynamic_pointer_cast<Receptionist>(emp2), nullptr);
    }

**Test 3:** Check that it is not possible to save an employee if their email or phone already exists in the container (Global Validation).

    TEST_F(EmployeeContainerFixture, FailToSaveWithDuplicateEmail){
        // Cria e guarda um Enfermeiro
        shared_ptr<Employee> emp1 = this->container->create(L"Ana", ..., L"duplicate@test.com", ..., "Nurse");
        this->container->save(emp1);

        // Tenta criar um Rececionista com o MESMO email
        shared_ptr<Employee> emp2 = this->container->create(L"Rui", ..., L"duplicate@test.com", ..., "Receptionist");
        
        // Verifica que o 'save' lança uma exceção (mesmo sendo classes diferentes, o email tem de ser único)
        EXPECT_THROW(this->container->save(emp2), std::runtime_error);
    }
